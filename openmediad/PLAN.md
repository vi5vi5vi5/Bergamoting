# openmediad — свой медиа-движок для Станции Мини 3 (план работ)

> Рабочая папка проекта. Протокол шины и разбор железа — в соседнем
> `../quasar messaging/PROTOCOL.md` (разделы 5, 8, 13 — про плеер и замену mediad).
> Досье колонки — `../mini3-dossier.md`. Доступ: `ssh -p 2222 root@192.168.1.12` (пароль пустой).

---

## 1. Что делаем и зачем

**Цель:** свой лёгкий медиа-движок на самой колонке, который воспроизводит звук из любых
источников (Яндекс-поток, Spotify, SoundCloud, meetup-Opus, Bluetooth-вывод) через одну точку,
и который можно довести до **полной замены штатного `mediad`**, чтобы вернуть его память.

**Главная ценность — универсальность**, а не экономия. Экономия памяти — бонус (см. §2).

**Принцип:** один «слив» (вывод в ALSA + арбитраж «кто сейчас играет») + сколько угодно
источников-«кранов», подключаемых к нему.

## 2. Честный приз по памяти (замерено 27.10.2026)

| Процесс | RSS | **Pss** (цена для системы) | Private_Dirty |
|---|---|---|---|
| mediad | 30 МБ | **16 МБ** | 4.8 МБ |
| platformd (уши Алисы) | 55 МБ | 41 МБ | 23 МБ |

- RSS завышен: 22 МБ — общий бинарник `maind`, посчитан каждой роли.
- Реальная цена `mediad` ≈ **Pss 16 МБ**; «железно его» ~5 МБ (Private_Dirty) + GStreamer-либы
  (`libquasar_gstreamer.so` 5.8 МБ + плагины), которые грузит, похоже, только он.
- **Полное снятие `mediad` вернёт ~10–14 МБ** (при свободных ~90–120 МБ). Заметно, не переворот.
- Вхолостую `mediad` ест **~0% CPU** (GStreamer разобран, пока не играет). Главный едок CPU и
  RAM — `platformd` (всегда-включённое прослушивание), его трогать нельзя без потери активации.

Вывод: делаем ради движка; память оправдывает проект только вместе с универсальностью.

## 3. Как вообще выводится звук (ALSA, кратко)

ALSA — звуковая система Linux, труба «программа → динамик». Программа отдаёт PCM (сырые сэмплы),
ALSA толкает в карту → усилитель → динамик. На колонке (`/etc/asound.conf`):

```
default (asym) ─ playback → speakers (plug) → dmix_speakers → hw:0,0 (усилитель ACM8625)
               └ capture  → multi_capture (8-канальный loopback hw:0,1: 3 микрофона + «HW feedback»)
```

> Исправление от 27.10.2026: раньше здесь стояла схема `softvol "Master" → dmix`, перенесённая из
> вики (она описывает Лайт). На Мини 3 проверено иначе — см. §13.

- `dmix_speakers`: ключ IPC 1024, 48 кГц, 2 канала, буфер 7680 кадров (160 мс), период 960 (20 мс),
  железо открыто в S16_LE. Это штатный смеситель: **к нему подключаются все клиенты**.
- Громкость — **аппаратный** контрол карты (`Master Playback Volume`, 0–255), не софтверный:
  все потоки через dmix слушаются кнопок и Алисы автоматически.
- Нам **не нужен GStreamer**: движок сам декодирует и отдаёт PCM нативному клиенту ALSA.
  Но клиент должен быть **32-битным** (см. §13) — это ключ к совместимости с dmix.

## 4. Ключевая развилка (решить до кода)

**Берём ли мы на себя воспроизведение голоса Алисы (TTS)?**

Через `mediad` идёт не только музыка: **TTS Алисы** (Opus-кадры на 9906, поле 29),
**будильники/таймеры**, **Bluetooth-плеер**, системные звуки, плюс `update_health_check` пингует
`mediad`, а callbacks трека (on_started/finished) нужны для очереди/«дальше».

- **НЕТ (шим):** движок делает только музыку, остальное остаётся штатному `mediad`.
  `mediad` жив → память не вернём, но риск низкий. Универсальность получаем.
- **ДА (полная замена):** движок берёт и TTS (свой Opus-декодер), и всё прочее → `mediad`
  можно выключить → ~10–14 МБ назад. Но ширина работы и риск максимальны.

**Рекомендация:** идти инкрементально — сначала шим (фазы 0–4), полную замену (фаза 5) делать
только когда шим обкатан и мы уверены в каждом канале. Решение по TTS = решение «делать ли фазу 5».

> СТАТУС РЕШЕНИЯ (27.10.2026): **TTS берём на себя.** Фаза 5 — целевая, не опциональная.
> Мотив пользователя: выводить ответы Алисы, например, в Bluetooth-наушники, с декодированием
> Opus на самой колонке. Следствия:
> - ответ Алисы приходит на 9906 как Ogg/Opus (команда тип 8, поле 29, плеер типа 2);
>   движок должен уметь **маршрутизировать поток по выходам** (динамик / Bluetooth / оба);
> - выход «наушники» — это ALSA-устройство `bluealsa` (a2dp-source уже запущен прошивкой),
>   а не штатный `default`; нужен выбор выхода на лету и обработка отвала наушников;
> - порядок работ остаётся инкрементальным: шим (фазы 0–4) → TTS и полная замена (фаза 5).

## 5. Выбор инструментов (решить на фазе 0)

- **Язык ядра движка:** Go (статика aarch64, как уже проверенный LED-агент `../logo-led test`:
  бинарник ~1.7 МБ, RSS ~2–7 МБ, собирается без возни). Рекомендация — Go для шины/движка.
- **Spotify:** переиспользовать **librespot** (Rust) отдельным процессом-источником, не
  переписывать. Движок запускает его и читает PCM/управляет им. (Так проще, чем spotiya
  в одном бинарнике, и память держим раздельно.)
- **ALSA из Go:** тонкая обёртка над `libasound` или запись в `default` через `aplay`-подобный
  путь; выбрать на фазе 1 по факту замера памяти.
- **Protobuf шины:** свой минимальный кодек конверта `{252,253}` (как в `../quasar messaging/tools/qipc.py`),
  без тяжёлых библиотек.

Бюджет памяти движка вхолостую: **цель < 5 МБ** (иначе съедает экономию). Правило: декодер и
буферы создаются только на время игры, в простое — только сокеты и малый heap.

## 6. Правила безопасности и обратимости (соблюдать всегда)

1. Всё своё — в `/data/opt` (переживает перезагрузку). Rootfs править только через
   `mount -o remount,rw /` → правка → `sync` → `mount -o remount,ro /`.
2. **Бэкап штатного `launch.json`** перед любым изменением; восстановление одной командой.
3. Никогда не трогать boot/bootloader/recovery/MTD. Не сбрасывать колонку. Не ставить OTA.
4. Каждая фаза **откатывается** (убить наш процесс / вернуть launch.json → колонка снова штатная).
5. Перед сносом `mediad` — убедиться, что наш демон поднимается сам и держит все каналы.
6. Тестировать так, чтобы потеря SSH не оставила колонку в нерабочем состоянии (сначала ручной
   запуск из SSH, автозапуск из `init.d` — только после обкатки).

## 8. План по фазам (каждая — проверяемая и откатываемая)

### Фаза 0 — Наблюдатель и инструменты
- **Делаем:** каркас проекта (Go), минимальный кодек конверта `{252,253}`, подключение к шине
  «лишним клиентом», логирование кадров. Выбор языка/ALSA-пути зафиксировать.
- **Проверка:** читаем `AliceState`/события плеера, умеем собрать и отправить кадр; поведение
  колонки не изменилось.
- **Откат:** просто убить процесс.
- **Выход:** есть надёжный R/W доступ к шине из своего кода.
- **СТАТУС: выполнена 27.10.2026** (чтение и сборка кадров проверены; отправка в живую шину
  намеренно не делалась — сборщики сверены побайтно с реальными кадрами). Итоги — в §11.

### Фаза 1 — Звук наружу + бюджет памяти
- **Делаем:** движок играет тестовый тон и локальный файл прямо в ALSA `default` (без GStreamer).
- **Проверка:** звук слышен; замер Pss вхолостую (<5 МБ цель) и под воспроизведение.
- **Откат:** убить процесс.
- **Выход:** подтверждён путь вывода и бюджет памяти.
- **СТАТУС: в работе (27.10.2026).** Сделано: ALSA/dmix, приёмник звука, выбор и проверка декодера CELT
  (§13). Не сделано: связка «Go-декодер → pipe → aplay» с замером задержки и Bluetooth-вывод.

### Фаза 2 — Прозрачный шим на 9906 (страховочная веха)
- **Делаем:** наш процесс слушает 9906, штатный `mediad` переносим на другой порт; проксируем
  **всё** в обе стороны без изменений.
- **Проверка:** музыка, **голос Алисы**, будильники, громкость, дисплей работают как раньше, с нами
  «в середине». Замер задержки.
- **Откат:** вернуть порт `mediad`, убрать шим.
- **Выход:** мы прозрачно сидим в разрыве и ничего не ломаем.
- **СТАТУС: выполнена (27.10.2026), итоги — §16.** Шим работает без правок rootfs (iptables REDIRECT + `omd shim`), 1826
  кадров сверено побайтно без расхождений, откат и страховка проверены; не переживает перезагрузку (решение за вами).

### Фаза 3 — Перехват музыки
- **Делаем:** в шиме ловим музыкальный `audio_play` (sub_name music) → играем своим движком
  (для начала — ту же Яндекс-ссылку, чтобы сверить поведение 1:1); события 127 синтезируем;
  TTS/будильники/BT пропускаем в штатный `mediad`.
- **Проверка:** «Алиса, включи музыку» играет через нас; Алиса по-прежнему говорит; «пауза/дальше»,
  громкость, прогресс/дисплей корректны; таймеры срабатывают.
- **Откат:** отключить перехват (режим чистого прокси фазы 2).
- **Выход:** музыкой владеем мы, система не замечает.

- **СТАТУС: выполнена частично (27.10.2026), итоги — §17.** Музыку Яндекса играет шим (`-music`), события сверены с настоящими
  побайтно, откат на mediad при ошибке потока работает; нет синтеза спектра для дисплея, не проверено на слух, постоянной установки нет.

### Фаза 4 — Источники
- **Делаем:** за нашим движком — интерфейс «играй вот это»; подключаем источники по одному:
  **librespot (Spotify)**, **SoundCloud**, **meetup-Opus**. Голосовые интенты («включи …»)
  маршрутизируем на нужный источник.
- **Проверка:** каждый источник играет, переключение между ними и штатным Яндексом корректно
  (один играет за раз, арбитраж чистый).
- **Откат:** выключить конкретный источник.
- **Выход:** универсальный движок работает; `mediad` ещё жив (для TTS и пр.).

### Фаза 5 — Полная замена `mediad` (опционально, цель-максимум)
- **Условие входа:** фазы 2–4 обкатаны; принято решение брать TTS на себя (§4).
- **Делаем:** движок берёт TTS (свой Opus-декодер → ALSA), будильники, системные звуки, отвечает
  на `update_health_check`, владеет ALSA. Узел `mediad` убираем из `launch.json` (rootfs rw,
  с бэкапом), наш демон — из `init.d/S99z…` со своим супервизором.
- **Проверка:** полный прогон всех функций Алисы без штатного `mediad` ≥ сутки; замер
  возвращённой памяти (ожидаем ~10–14 МБ).
- **Откат:** вернуть `launch.json` из бэкапа + reboot → штатный `mediad` на месте.
- **Выход:** `mediad` не запускается, память возвращена, всё работает.

## 11. Итоги фазы 0 (27.10.2026)

Всё ниже проверено на живой колонке (прошивка `.117`) и сверено независимым дампом `tcpdump`.

**Что построено:** `omd observe` (клиент-наблюдатель на колонке), `omd pcap` (разбор записей, в т. ч.
`-voice-dir` для сохранения голоса Алисы в `.ogg`), пакеты `pb` (protobuf без схем), `wire` (кадры и
конверт 252/253, сборщики `CancelDialog`/`PausePlayback`), `quasar` (окна на сообщения), `obs`.
Тесты: сборщики совпадают побайтно с реальными кадрами `maind --cli`; разбор реальной записи
(`OMD_PCAP=…`) воспроизводит все виды сообщений. Тесты нашли ошибку в сборке TCP-потока при
повторе сегмента — исправлена.

**Измерения наблюдателя на колонке** (статика arm64, 3,1 МБ, `GOGC=25`): RSS 2,3 МБ,
Pss ≈ 4,0 МБ (с общими страницами бинарника), Private_Dirty 1,1 МБ, 8 потоков, CPU в простое 0.
Бюджет «<5 МБ» выполнен — но это только наблюдатель, без декодера и вывода звука.

**Что узнали о шине**
1. Пассивный клиент на 9875 и 9906 безопасен: при подключении получает приветствие (`Handshake`,
   29 возможностей) и текущее состояние; при отключении соединения закрываются чисто (проверено
   с положительным контролем: 9875: 1→2→1, 9906: 4→5→4 клиента).
2. **`mediad` рассылает события плеера всем клиентам.** Каждое событие приходит всем: 4 соединения
   `platformd` + наш наблюдатель = ровно 5 копий (111 событий у нас ↔ 555 в дампе, расхождений 0).
   Значит, состояние воспроизведения можно отслеживать из клиентского режима, без шима.
3. **Команды плееру клиенту не видны** (идут между другими соединениями). Чтобы их видеть и
   перехватывать — шим (фаза 2) или pcap.
4. **Голос Алисы:** одна команда `AudioCommand` несёт весь ответ целиком (23 КБ для «12:46.»,
   8 КБ для «Включаю.»). Порядок: `voice-start` → `voice-chunk` (Ogg/Opus) → `voice-eos`;
   после события `ENDED` — `release`. Формат: **Opus, 1 канал, 48 кГц, режим CELT fullband,
   кадр 20 мс, ~77 кбит/с**, кодировщик ffmpeg (`Lavf57`). Следствие для наушников: нужен
   декодер **с поддержкой CELT** (SILK-only декодеры на чистом Go не подойдут). Варианты —
   проверить на фазе 1: libopus статикой через `zig cc` (путь из вики hackalice, раздел
   «Сборка своего софта») либо готовый pure-Go CELT, если найдётся. Файлы голоса для
   экспериментов извлекаются командой `omd pcap -voice-dir`.
5. **Порядок для музыки:** `prefetch` трека приходит одновременно со стартом голоса, а `play` —
   только после `release` голосового плеера (~1 с после конца речи). Пауза: команда `pause`,
   событие `PAUSED` через ~40 мс.
6. **Подводный камень для интентов (фаза 4):** в режиме «Алиса слушает дальше после ответа»
   распознанный текст приходит с префиксом «Алиса» **без запятой** («Алиса включи музыку»).
   Разбор в `spotiya` срезает только «алиса, » — свой разбор должен нормализовать оба варианта.
7. При подключении к 9906 сервис присылает `Remoting ClockStorage` (метод 31) — назначение не
   изучалось.

**Ошибки процесса, которые стоит помнить:** две мои проверки сначала дали ложные результаты
(неверный hex порта; самосовпадение `grep` по cmdline). Правило на будущее: каждая проверка
«всё чисто» должна иметь положительный контроль, то есть уметь показать «грязно».

**Следующий шаг — фаза 1:** вывод звука в ALSA без GStreamer. Первые вопросы: декодер CELT
(см. п. 4), поведение `dmix`/EBUSY при параллельной игре штатного стека, замер памяти с декодером.

## 12. Структура папки

```
openmediad/
  PLAN.md            — этот план
  README.md          — короткая навигация
  cmd/omd/           — инструмент разработки: observe, pcap, pcmwatch, voice-play, shim (-music), shimcheck, music-test
  internal/pb/       — protobuf без схем (разбор и сборка)
  internal/wire/     — кадры шины, конверт 252/253, сборщики команд
  internal/quasar/   — типизированные «окна» на сообщения (AliceState, AudioEvent, AudioCommand…)
  internal/obs/      — описание кадров, клиент-наблюдатель, разбор pcap, сверка сторон шима (shimcheck)
  internal/shim/     — прозрачный посредник на 9906 (кадры 1:1, сводка, слушатель закрывается при отказе сервиса)
  internal/player/   — модель плеера mediad: сборка событий 127 (побайтная сверка), автомат состояний, кэш паузы
```

**Оговорки к этим опытам**
- Смешение на слух никто не подтверждал (в это время вы говорили с Алисой): вывод сделан по счётчикам

- Опыт пересёкся с вашим диалогом: два «лишних» голосовых воспроизведения были ответами Алисы вам

  целиком (только обычные предупреждения прошивки при старте трека).

**Сознательно не проверялось:** 64-битный клиент в общем dmix. Состояние смесителя лежит в общей памяти
с полями типа `snd_pcm_uframes_t`, размер которого у 32- и 64-битных процессов разный, так что чужая
разрядность, вероятно, испортила бы смеситель штатного стека. Это рассуждение об устройстве alsa-lib,
на колонке не проверено — рисковать звуком штатного стека ради проверки не стали.
**Решение:** приёмник звука — 32-битный нативный клиент (системный `aplay` или свой armv7-помощник),
а сам движок (aarch64, статика, без CGO) отдаёт ему PCM через pipe.

**Цена приёмника:** `aplay`, играющий тишину: RSS 1,7 МБ, **Pss ≈ 0,5 МБ**, Private_Dirty 0,2 МБ, 1 поток.
Модель «движок → pipe → aplay» вхолостую ничего не стоит (aplay живёт только на время звука) и
≈0,5 МБ при игре. Через плагин bluealsa `aplay -D bluealsa:…` должен выводить в Bluetooth — **не проверено**.

**Оценка «декодировать родным GStreamer колонки» (вариант 0):** работает (`maind --gst-launch
"filesrc ! decodebin ! audioconvert ! audioresample ! … ! filesink"` декодирует оба чанка голоса), но
процесс занимает **~30 МБ RSS (пик)** и ~0,5 с на запуск и декод одного ответа. Как временное решение
для «голос в наушники» годится, как целевое — тяжело и по памяти, и по задержке.

**Декодер CELT — итог сверки (разрешено пользователем: только `go-opus` v1.3.0, изолированный модуль в
scratchpad, без `gopus`).** Эталон — вывод родного декодера колонки (GStreamer) на двух реальных чанках голоса.
- **Точность:** оба чанка на ПК (amd64) и на колонке (linux/arm64) дали **одни и те же** цифры: макс. ошибка
  **6 из 32768** (около −75 дБFS), RMS 0,90–0,94, **SNR 74 дБ**; побитово совпало 58,2% и 62,3% отсчётов.
  Два API библиотеки (`opus.Decoder` и `oggopus.DecodeInterleaved`) дали идентичный результат. То есть
  декодер **не побитово идентичен** выводу колонки, но различие неслышимо; причину не установили
  (возможны другая сборка libopus на колонке — с фиксированной точкой — или преобразование float→S16 в
  GStreamer). Заявленное «побитово как libopus» на наших данных проверить нечем (libopus на ПК нет).
  Эталон сдвинут на 312 отсчётов (6,5 мс) относительно нашего вывода: длина эталона правильная (гранула минус
  pre-skip: 111733 и 40402), но GStreamer не выбросил pre-skip в начале, поэтому его вывод «запаздывает» на
  столько же, а хвост на столько же короче. Наш вывод следует RFC 7845 и совпадает с эталоном по длине точно;
  сравнивалась общая часть. (Первая версия этого объяснения считала «обрезку хвоста» от полного декодирования
  и была неточной.)
- **Скорость на колонке** (Cortex-A53, под нагрузкой: load average 4–6, `nice 5`): **≈25 мс на 1 с звука
  (≈40× быстрее реального времени)**; ответ в 2,3 с декодируется за ≈60 мс. Новый декодер на каждый ответ
  не дороже долгоживущего (26,0 против 25,3 мс/с). Для сравнения: GStreamer колонки — ≈0,5 с на ответ.
- **Память на колонке** (прибор измерения без аллокаций; процесс — статика arm64, `GOGC=25`):
  | Точка | RSS | Pss |
  |---|---|---|
  | старт процесса (рантайм Go + разобранные пакеты) | 2,5 МБ | 2,6 МБ |
  | после `NewDecoder` | 2,9 МБ | 3,2 МБ |
  | после 64 с декодирования одним долгоживущим декодером (A) | 2,9 МБ | 3,4 МБ |
  | после 40 ответов «новый декодер на каждый» (B), пик | 4,8 МБ | 4,8 МБ |
  | после GC + FreeOSMemory (C) | 3,7 МБ | 4,1 МБ |
  Сам `Decoder` — ≈22 КБ кучи при создании; в установившемся режиме ≈0,5 аллокации (0,3 КБ) на 1 с звука,
  то есть практически без аллокаций. **Вывод: держать ОДИН долгоживущий декодер и делать `Reset()` между
  ответами** — память остаётся плоской (≈3 МБ Pss), а схема «новый декодер на ответ» раздувает кучу до
  ≈5 МБ. Первый замер (пик 5,3 МБ) был завышен собственным прибором и стендом — он выделял память между
  замерами; прибор переделан и замер повторён.
- **Бюджет:** движок с декодером ≈3,5 МБ Pss + `aplay` ≈0,5 МБ на время звука ≈ **4 МБ** при цели <5 МБ.
  Для сравнения вариант 0 (GStreamer): ≈30 МБ RSS и ≈0,5 с на ответ — в ~10 раз тяжелее и ~8 раз медленнее.
- **Решение: `go-opus` v1.3.0 принят как декодер CELT.** Условия: версия зафиксирована, исходники
  `go-opus`, `tphakala/simd` v1.14.0, `golang.org/x/sys` — вендорить в репозиторий (`go mod vendor`)
  и пересчитать хэши; статический аудит импортов чистый (нет net/exec/plugin), полного ручного аудита нет.
  **Не проверено:** длинные ответы и другие фразы (проверено два чанка одним голосом/режимом), поведение
  при потере/порче пакетов, `gopus` (не запускался и не нужен, пока `go-opus` устраивает).

**Дальше (остаток фазы 1):** (a) вендорить `go-opus` и подключить к движку; (b) минимальный вывод
«Go-декодер → pipe → `aplay`» на настоящем чанке голоса Алисы, замер задержки до первого звука;

## 14. Фаза 1: связка «Go-декодер → pipe → aplay» (27.10.2026, промежуточные итоги)

**Сделано**
- `go-opus` v1.3.0 вместе с `tphakala/simd` v1.14.0 и `golang.org/x/sys` v0.49.0 вендорен в `vendor/` (≈2 МБ,
  230 файлов); сборка и тесты идут с `-mod=vendor`, `go mod verify` отвечает «all modules verified».
  Происхождение, лицензии и хэш дерева — в `THIRD_PARTY.md` и `vendor.sha256`. Проверка целостности
  проверена положительным контролем: изменение одного байта она ловит.
- Новые пакеты: `ogg` (потоковый разборщик контейнера: куски любого размера, перетекание пакетов между
  страницами, потерянное начало пакета), `opusstream` (один долгоживущий декодер, `Reset()` между ответами,
  pre-skip, подрезка хвоста по гранулe, `OutputGain`), `sink` (обёртка над `aplay`), `clock` (CLOCK_MONOTONIC),
  `pcm` (разбор `/proc/asound/.../status` и `trigger_time`). Команды: `omd voice-play`, `omd pcmwatch`,
  `omd observe -mono`.
- Тесты самодостаточны: тон кодируется кодировщиком `go-opus`, заворачивается в Ogg собственным писателем
  (в том числе с перетеканием пакетов между страницами) и декодируется при нарезке потока по 1, 5, 64, 1000 Б и
  целиком; вывод не зависит от нарезки. Реального голоса Яндекса в репозитории нет. Все тесты проходят на ПК,
  тесты `sink` проходят и на самой колонке — включая две SIGINT-проверки, которые на Windows пропускаются.

**Решения, вшитые в код**
- Приёмник — системный 32-битный `aplay` (причина в §13); `-c 1`: из моно в стерео превращает `plug` ALSA;
  `-R` на целом чанке ни на что не влияет (см. замер ниже), параметр оставлен настраиваемым.
- **`aplay` никогда не убивается SIGKILL** — только закрытие stdin или SIGINT (проверено тестами на колонке):
  оборванный посреди записи процесс может оставить общий смеситель в состоянии, когда замолкает вся колонка.
- Один `opusstream.Stream` на весь процесс (замер §13: так память остаётся плоской).

**Измерено на колонке**
- Декодирование в составе `omd`: 58,6 мс на ответ 2,33 с и 21,1 мс на 0,84 с (40× быстрее реального времени);
  первый вызов не медленнее последующих.
- Длина вывода совпала с эталоном колонки точно: 111733 и 40402 отсчёта (= гранула − pre-skip).
- Функциональный прогон реального чанка «Включаю.» (поверх играющей музыки): `exec` aplay 3,1 мс, первый PCM
  через 4,1 мс, запись в pipe закончена за 118 мс, `aplay` завершился через 921 мс при клипе 0,84 с, код
  возврата 0. Тот же чанк кусками по 1000 Б с заранее запущенным `aplay`: первый PCM через 2,9 мс.
  Процесс `omd` при этом держит 4,0–4,6 МБ RSS (декодер, пакеты чанка, pipe). Остатков процессов нет.

**Задержка до запуска PCM — замер в тишине.** Молчаливая копия чанка «Включаю.», по 5 прогонов на сценарий.
t0 = «чанк получен»; trigger = момент запуска PCM ядром (`trigger_time`, CLOCK_MONOTONIC).

| Путь | trigger, медиана | разброс |
|---|---|---|
| S1 `aplay` по умолчанию, холодный запуск | 15,8 мс | 14,1–28,9 |
| S2 `-R 1`, холодный | 16,1 мс | 13,2–23,5 |
| S3 `-R 1`, буфер 100 мс / период 20 мс, холодный | 19,8 мс | 14,9–21,7 |
| S4 `-R 1`, `aplay` запущен заранее | 1,9 мс | 1,8–9,7 |
| S5 `-R 1`, буфер 100/20, запущен заранее | 1,9 мс | 1,8–2,3 |
| **штатный путь Алисы (`mediad`)**, 4 ответа | **62 мс** | 36–69 |

- Холодный запуск `aplay` (exec + `libasound` + открытие dmix) стоит ≈14 мс; заранее запущенный — ≈2 мс. Наша связка
  запускает PCM примерно в 4 раза быстрее штатной при холодном запуске и примерно в 30 раз — при запущенном заранее.
- На целом чанке `-R` и размер буфера не влияют (S1 ≈ S2 ≈ S3 в пределах разброса). Первый прогон S4 (9,7 мс) — после
  долгого простоя; остальные 1,8–3,3 мс.
- **Штатный путь:** в 3 из 4 ответов `voice-start` и чанк приходят в одну и ту же миллисекунду (до запуска PCM 54–69 мс),
  в одном `voice-start` опередил чанк на 331 мс (36 мс). Вывод для проекта: поднимать приёмник «по `voice-start`» запаса не
  даёт; надо делать это по более раннему сигналу (состояние Алисы BUSY за ≈1 с до речи) или держать `aplay` «тёплым».
- **Поток реального времени** (искусственный стенд: по 100 мс данных раз в 100 мс; у настоящего TTS другая картина):
  умолчание стартует через ≈120 мс без `underrun`; любое `-R` до 80 мс — через 20–30 мс, но с 5–8 `underrun` за секунду
  (запаса на дрожание нет). Значение для возможного потокового TTS по частям не подобрано. Прежнее утверждение, что без
  `-R` короткая фраза зазвучит «после конца записи» и что буфер `aplay` 500 мс, оказалось неверным: буфер клиента
  ограничен смесителем (160 мс), а на быстром потоке разницы нет.
- Что НЕ измерено: `trigger_time` — это запуск потока в железо, а не звук в динамике. Хвост от запуска до звука
  (буфер смесителя 160 мс, период 20 мс) общий для обоих путей и не мерился; поэтому вывод «наш путь быстрее штатного
  на ≈45–60 мс до запуска PCM» корректен, а абсолютная задержка до звука неизвестна.
- Слух: «Включаю.» поверх музыки слышен один раз из двух (второй, по словам пользователя, мог быть не замечен).
  Повторный слышимый прогон в тишине (реальный чанк «Включаю.», `aplay` запущен заранее) — пользователь подтвердил:
  звук слышен и чистый. Связка «Go-декодер → pipe → aplay» по звуку признана рабочей.

**Ещё не сделано:** прогон на других фразах и длинном ответе (приходит ли он несколькими командами); Bluetooth-вывод
(`aplay -D bluealsa:…`); подключение связки к шине (шим, фаза 2).

## 15. Bluetooth-наушники и маршрутизация потоков (27.10.2026)

**Запрос пользователя:** подключать наушники к колонке по Bluetooth, музыку выводить в наушники, а ответы Алисы оставлять
на штатных динамиках (или, как в §4, наоборот). Ответ на уровне принципа: да, это естественно ложится на движок как
маршрутизатор «класс потока → выход». Что реально проверено и что нет — ниже.

**Проверено на колонке (только чтение: ничего не спарено, сканирования не было)**
- BlueZ 5.70, `bluealsa` 4.1.1, чип Amlogic (`hciattach aml`, `hci0`, HCI 5.0). `bluealsa` запускается с
  `-p a2dp-sink -p a2dp-source -p hfp-ag --sbc-quality=high`. **Кодек только SBC** (A2DP source и sink; HFP — CVSD, mSBC).
- UUID адаптера содержат `Audio Source` (110a) и `Audio Sink` (110b), AVRCP, HFP AG; роли central и peripheral. То есть
  стек заявляет A2DP Source и может подключаться к наушникам. **Реальное соединение с наушниками НЕ проверено.**
- Сейчас `Pairable: no`, `Discoverable: no` (штатный интерфейс включает спаривание только для телефонов); спарено 5
  устройств, подключённых нет, PCM `bluealsa` нет.
- В `/etc/asound-bluetooth.conf` PCM `bluetooth` — это `softvol` «Bluetooth Master Playback Volume» поверх `speakers`,
  то есть приём музыки С телефона НА динамики, а не вывод на наушники. Для наушников нужен другой PCM:
  `bluealsa:DEV=<MAC>,PROFILE=a2dp` (плагин `libasound_module_pcm_bluealsa.so` на месте); для моно и произвольной частоты
  удобнее `plug:bluealsa:...`.
- Громкость `Master` — аппаратная (усилитель), на Bluetooth-выход не влияет. Понадобится своя громкость (программный
  множитель в маршрутизаторе или AVRCP/bluealsa) и мост от кнопок громкости колонки.

**Варианты маршрутизации**
- **R1. Источник наш** (Spotify через librespot, SoundCloud, meetup, голос Алисы после перехвата): движок сам выбирает выход —
  `bluealsa` или `default` (динамики), с запасным вариантом «нет наушников → динамики». Самый простой путь.
- **R2a. Штатная музыка Яндекса → наушники через трубу ALSA** (голос Алисы остаётся на динамиках). Плеер музыки `mediad`
  (тип `TRACK`) пишет в PCM с плагином `file`, который пишет в FIFO; наш процесс читает FIFO и играет в наушники или в
  динамики. **Механика проверена** на колонке на изолированном конфиге (`ALSA_CONFIG_PATH` только для тестового процесса,
  системные файлы не менялись), источник — реальный клип 2,33 с через штатный `maind --gst-launch`:
  читатель без ограничений — конвейер отработал за 0,54 с (быстрее реального времени, при этом в трубу ушло в 4,7 раза
  больше нужного: приёмник добивает паузы тишиной); читатель ровно в реальном времени — 2,60 с, +3,5% байт; читатель втрое
  медленнее — 6,57 с, +0,4% байт. Все три — без ошибок и потерь: **GStreamer колонки не держит темп сам, его тормозит
  читатель FIFO**, то есть темп воспроизведения задаёт наш маршрутизатор.
  **Не проверено и опасно:** (1) можно ли в `quasar.cfg` задать `deviceName` только для типа `TRACK` (по логу
  `mediad` итоговые параметры типа содержат `deviceName`, значит, переопределение вероятно, но не пробовалось);
  (2) нужна правка rootfs (`quasar.cfg`, `asound.conf`) и перезапуск Quasar — не делалась, пока пользователь не дома;
  (3) без читателя открытие FIFO блокируется, и музыка молчит, поэтому маршрутизатор обязан быть всегда запущен и
  перезапускаться (ловушка отката: вернуть исходный `quasar.cfg`); (4) поведение `mediad` при остановке читателя,
  прогресс и события — не изучалось.
- **R2b. Шим на 9906 (фаза 2) перехватывает `audio_play` и играет сам.** Для музыки Яндекса нужен свой декодер AAC в
  MP4 плюс AES (`decode_key`), это тяжело; для Spotify не нужен вообще (там R1).
- **R3. Голос Алисы в наушники:** шим не пропускает `voice-chunk` в `mediad`, а отдаёт нашему декодеру → `bluealsa`
  (или оба выхода). Декодер уже готов (§13–§14), включая цепочки потоков (ниже).

**Не проверено / риски:** реальный A2DP Source на этом чипе; процедура спаривания (штатный интерфейс не умеет, нужны
`bluetoothctl pairable on` и режим спаривания у наушников; агент `just-works-bluez-agent` уже запущен); качество и
задержка SBC (обычно 100–200 мс, поверх этого буфер клиента); AVRCP; как себя поведёт штатный стек (`platformd` управляет
Bluetooth и может отреагировать на неожиданное устройство); вернуть `Pairable: no` после проверки.
Скрипт проверки: `scripts/bt-test.sh` (`status` — только чтение; `scan`, `pair`, `play`, `disconnect`, `remove`
меняют состояние и требуют наушников; **не запускался**).

**Прочие находки этого дня**
- **Длинный ответ Алисы — цепочка самостоятельных Ogg-потоков.** Каждый `voice-chunk` имеет свои страницы BOS/EOS,
  `OpusHead`/`OpusTags`, серийный номер и гранулы (замер: два потока по ≈20 КБ, ≈2 с каждый; второй пришёл через 42 мс
  после первого, `voice-eos` ещё через 43 мс). Мой `opusstream` сначала этого не умел: второй `OpusHead` он принял бы за
  аудио. Исправлено: BOS-страница с `OpusHead` начинает новый поток — сбрасываются декодер (RFC 7845) и счётчик подрезки
  по гранулe; общий `Samples()` считается по всей цепочке; тест на цепочку (440 и 880 Гц тремя способами подачи)
  проходит. Реальная цепочка из двух потоков на колонке: 3,98 с звука за ≈100 мс (40× реального времени). Длина вывода
  191106 отсчётов, а не 191145 «по гранулам»: гранула второго потока на 39 отсчётов больше числа декодированных
  отсчётов, а лишнего декодер выдать не может.
- **Холодное железо.** Если PCM закрыт (никто не держит dmix), запуск не медленнее: холодный `aplay` ≈16 мс на
  прогретом процессоре, заранее запущенный 1,9–3,1 мс, как и при открытом dmix. Первые два холодных прогона 37,6 и
  28,9 мс (`exec` 8 мс против 1 мс) похожи на раскачку частоты процессора после простоя (в системе есть поток
  `cfinteractive`); это предположение, не проверялось. Амплитуда звука после `trigger` (включение усилителя) не мерилась.
- **PCM закрывается примерно через 30 минут простоя:** `mediad` держит кэшированные плееры (`cleanPlayerTimeoutSeconds` 1800),
  и пока кэшированный плеер жив, PCM стоит в PREPARED. Замеры §14 с PREPARED относятся к этому состоянию.
- **Шум в `dmesg`:** 32-битный `dropbear` вызывает syscall 403 (`clock_gettime64`), которого нет в ядре 4.9; ядро печатает
  дамп регистров при каждом SSH-подключении, а `dropbear` откатывается на старый вызов. Безвредно.
- **`maind --gst-launch` не завершается на невалидном конвейере** (в прошивке нет `audiotestsrc`; процесс остаётся спать с
  ≈30 МБ). Мой первый опыт с трубой повис на этом и ничего не показал; все такие опыты теперь идут со сторожем по
  времени (SIGTERM, затем SIGINT). Настоящий PCM при этом не затрагивался; зависшие процессы убиты, остатков нет.

## 16. Фаза 2: прозрачный шим на 9906 (27.10.2026)

**Итог:** шим работает и откатывается. `omd shim` стоит между platformd и настоящим audioclient (`mediad`, 9906) и
пересылает кадры 1:1. Через него прошли ответы Алисы, музыка (команды play/prefetch/pause и события плеера) и таймер
(подтверждение голосом, звонок, остановка «стоп»); откат проверен несколько раз, страховка — убийством шима `SIGKILL`.
**Постоянной установки нет** — шим и правило пропадают при перезагрузке; это сознательно (см. «Решения для фазы 3»).

**Как устроено**
- Порт `mediad` не переносим: корень смонтирован `ro` (ubifs), правка `quasar.cfg`/`launch.json` постоянна и рискованна.
  Вместо этого правило `iptables -t nat -I OUTPUT 1 -p tcp -d 127.0.0.1 --dport 9906 ! -s 127.0.0.2 -j REDIRECT --to-ports
  19906`. Шим слушает `127.0.0.1:19906`, а к настоящему сервису ходит **с адреса 127.0.0.2** (loopback — вся сеть /8), поэтому
  правило его самого не трогает. В ядре 4.9 есть `nat`/`REDIRECT`; сначала это проверено узким правилом только для
  источника 127.0.0.3 с контрольным клиентом (контроль шёл напрямую, тестовый — через шим, данные те же).
- Включение — `scripts/shim-on.sh`: шим → страж `shim-guard.sh` → правило → `SIGTERM` для `mediad` → штатный лаунчер
  поднимает новый `mediad` сразу (завершение ≈3 с) → **platformd переподключает все 4 клиентских соединения через шим
  за ≈1 с**. Выключение — `scripts/shim-off.sh`: правило снято, шим остановлен, platformd возвращается напрямую
  (во всех прогонах — меньше секунды). В rootfs ничего не пишется.
- **Страж** (`/data/opt/bin/shim-guard.sh`): снимает правило и останавливает шим, как только шим умер или вышло время
  (по умолчанию 1500 с, продлевается через `/tmp/shim.deadline`). Проверено: `kill -KILL` шима → правило снято за ≈0,9 с,
  platformd вернулся к `mediad` напрямую ещё за ≈0,9 с, Алиса ответила.
- У platformd **4 постоянных клиентских соединения** к 9906; события плеера рассылаются на все четыре, а команды идут
  по одному (в записях у трёх соединений 0 кадров к сервису). Шим сохраняет это, открывая своё исходящее соединение
  на каждое входящее.
- Шим работает по кадрам: читает `[u32 LE длина]` и тело, пишет одним вызовом, потом отдаёт копию наблюдателю (сводка по
  типам и задержка). Если поток перестал быть похож на кадры, остаток копируется как есть. Обрыв посреди кадра досылается
  как есть. `FIN` передаётся дальше, обратная половина ждёт 5 с.

**Проверено**
- **Побайтно (независимо от шима):** `omd shimcheck` по записи `tcpdump -i lo` обеих сторон шима сравнивает кадры (sha256 и
  размер) клиентской и сервисной стороны и меряет добавляемую задержку по меткам пакетов одних часов. Три прогона: 659 +
  765 + 402 = 1826 кадров, **расхождений 0**, лишних сервисных соединений с данными 0. Тесты прибора: искажённый кадр, лишний
  трафик и переиспользование порта клиента ловятся.
- **Задержка шима** (tcpdump, одни часы): к сервису p50 0,49–0,62 мс, p99 4,5–7,2 мс; к клиенту p50 0,39–0,76 мс,
  p99 4,4–11,7 мс, максимум 14,3 мс. В первом прогоне шим шёл без `nice`, дальше с `nice -n -10`: хвост p99 стал
  4,4 и 8,1 мс, максимум 9,5 и 9,3 мс; но нагрузка в прогонах разная, так что это намёк, а не доказательство.
- **От команды голоса до запуска PCM** (первый `voice-chunk` → `trigger_time`; серии по 6 коротких ответов, одни и те же
  фразы). После рестарта `mediad` PCM закрывается после каждого ответа (кэшированного плеера нет), поэтому сравнивались
  четыре сочетания:

  | | горячий PCM (на паузе кэшированная музыка) | холодный PCM (свежий `mediad`) |
  |---|---|---|
  | напрямую | 61,4 мс (40,7–76,3) и 68,4 мс (53,8–85,9) | 76,0 мс (45,3–85,9) |
  | через шим | 62,7 мс (43,6–79,8) | 72,9 мс (56,7–98,1) |

  Разброс между одинаковыми сериями (61,4 против 68,4) больше, чем разница с шимом; различимого эффекта нет. Холодный PCM
  добавляет ≈10 мс сам по себе (это следствие рестарта `mediad`, не шима). Старый замер штатного пути — 62 мс (36–69) — совпал.
  Чанк в «напрямую» — по метке tcpdump (часы сведены через `observe -mono`), в «через шим» — по монотонной метке самого шима.
- **Музыка:** «включи музыку» → `play` (9,8 КБ) и `prefetch`, события прогресса, пауза из `maind --cli` ('o'); PCM переходит

- **Память шима:** Pss 2,46 МБ (анонимной 1,2 МБ, 8 потоков), RSS 3,9–4,9 МБ — замер на стороне с двумя подключёнными

- **Откат и чистота:** после каждого опыта правил `nat OUTPUT` нет, процессов шима, стража и tcpdump нет, временных файлов
  нет, platformd подключён к `mediad` напрямую (4 соединения), Алиса отвечает.

**Находки и исправления по ходу**
- **Лавина попыток подключения при рестарте `mediad`.** Пока `mediad` отсутствует (≈3 с), platformd пробует переподключаться;
  первая версия шима принимала соединение, не могла дойти до сервиса и обрывала его, клиент видел «подключился и сразу
  сброс» и повторял сотни раз в секунду (1043 попытки за 3 с, журнал шима 188 КБ в tmpfs, в `maind.log` около тысячи
  предупреждений `Connection reset by peer`). Исправлено в два шага: журнал отказов не чаще строки в секунду; главное —
  **шим закрывает слушатель, пока сервис недоступен**, и ядро отвечает клиентам отказом, как у настоящего сервиса (когда
  сервис ответил на пробное соединение, слушатель открывается снова). Результат на колонке: в разрыв попала 1 попытка,
  остальные ≈11 отказаны ядром, предупреждений в `maind.log` нет, платформа повторяет реже. Тесты:
  `TestRunRefusesWhileServiceDown`, `TestRefusedIsLoggedRarely` (25 прогонов подряд зелёные).
- Первая версия `shimcheck` путала соединения: рассылки сервиса одинаковы у всех четырёх клиентов, а ответ NAT на обратном пути
  виден в записи с портом 9906, не 19906. Сопоставление исправлено (долгие соединения по SYN в окне 200 мс, совпадению кадров
  и близости длин потоков; короткие соединения времён простоя считаются отдельно).
- Чтение `pcap` вынесено в общие `readPcap`/`parseTCP`; разбор старых записей не изменился (694 строки совпадают с сохранённым).

**Чем шим отличается от штатного пути (честный список)**
1. `mediad` видит клиентов с адреса 127.0.0.2, а не 127.0.0.1.
2. Каждый кадр проходит лишний шаг: медиана +0,4–0,8 мс, хвост до ≈14 мс (по меткам tcpdump).
3. При включении `mediad` **перезапускается**: теряются кэшированные плееры (в том числе поставленная на паузу музыка, так что
   «Алиса, продолжи» после включения шима не сработает), PCM закрывается после каждого ответа, пока снова не появится
   кэшированный плеер.
4. Когда шим открывает слушатель, он делает одно пробное соединение к `mediad` (для сервиса это короткий клиент).
5. Лишний процесс: ≈2,5 МБ Pss.
6. В записи `tcpdump -i lo` клиентская сторона видна на порту 19906, а ответ на 9906 (обратная замена NAT).

**Не проверено**
- Звук на слух (вас не было дома): ответы и музыка судились по переходам PCM, `outputSpeech` в журнале платформы и тайминга;

- Поведение при перезапуске самого platformd с включённым шимом; автозапуск при загрузке.
- **Побочное наблюдение, причина не установлена:** `Master` был 115 (45%) в 15:17 UTC, стал 126 (49%) к 15:52. Звонок таймера

  Громкость я не трогал и не возвращал: возможно, её изменили вы или адаптивная громкость.

**Решения для фазы 3 (за вами)**
- **Постоянство.** Правило и шим должны появиться **до** того, как platformd подключится к `mediad`. Есть ваш хук

## 17. Фаза 3: перехват музыки в шиме (27.10.2026)

**Итог:** `omd shim -music` сам играет музыку Яндекса вместо `mediad` и сам рассылает события плеера. Алиса при этом
работает: «включи музыку», «следующий трек», «пауза», «продолжи», «перемотай», «который час» поверх музыки, «выключи музыку»
прошли через шим; platformd принял синтезированные события (после ENDED сам пошёл к следующему треку). Голос Алисы,
таймеры, фокус, громкость остаются у настоящего `mediad` (команды не перехватываются). **На слух не проверено** (см. ниже).
Включение: `ssh … 'sh -s -- 900 "-music"' < scripts/shim-on.sh`, откат: `scripts/shim-off.sh` (как в фазе 2; постоянной
установки по-прежнему нет, по решению пользователя). Если поток не открылся, команда `play` возвращается настоящему `mediad`.

**Что перехватывается.** Только плеер audio (`22.1 == 1`): `prefetch`, `play`, `pause` (поле 4), `crossfade` (поле 50),
`release`, перемотка «AUDIO_REWIND directive» (поле 13, `13.2` = секунды как double). `focus` (поле 39: 1 — диалог занял
фокус, 0 — отдал) пересылается `mediad` как раньше, а шим дополнительно приглушает музыку. Команды плееров, которых шим
не знает, и всё остальное идут `mediad` без изменений.

**Модель плеера mediad (по записям, `internal/player`)**
- Каждая команда `play` — новый идентификатор плеера. `prefetch` создаёт плеер заранее, `play` с тем же id запускает его.
  События после `prefetch` не приходят. Освобождение — `release`.
- События: `STARTING` через ≈14 мс после `play`; `PLAYING` ещё через ≈7 мс, если поток уже открыт (prefetch / кэш), иначе
  через ≈0,55–0,63 с; сразу за ним первый `progress`; `flag` (вид 6) через ≈290 мс после старта и ≈300 мс после смены
  фокуса (поле 17: 1 — громкость обычная, 0 — приглушена); `progress` каждые ≈1,06 с (в записях 1,054 с, у шима 1,058–1,069 с).
  Позиция — поле 3.28 (мс), целые секунды — 3.12, длительность — 3.6 (до готовности конвейера поля нет).
- `pause` → `PAUSED` через ≈24 мс. Если сразу за `pause` (до 5 мс) идёт `play` другого плеера («следующий») — у старого
  только `ENDED`; если того же трека (перемотка) — `PAUSED`, затем `ENDED`.
- Возобновление — новая команда `play` с `offset_ms` = позиция паузы. mediad берёт кэшированный плеер: в событиях остаются
  URL и зеркала (3.2, 3.42), `vsid` и `mark` прежнего открытия, у дескриптора пропадает поле 26 и появляется 30.
- **Событие плеера = дескриптор из команды play с правками:** к URL (3.2, 3.42) дописывается `?vsid=…`, убирается поле 18,
  в 21 добавляется третье число (−14.0 — целевая громкость), добавляются 12 (секунды), 22 (случайный uuid на каждое
  событие), 28 (позиция, мс), по условиям 6 (длительность), 29 (CLOCK_MONOTONIC, мс) и 30; 26/27 по правилу «готовый плеер»;
  после `crossfade` появляются 35 и 46. Верхний уровень: 1 вид, 2 состояние, 3 дескриптор, 4 плеер, 5 время запуска
  (epoch мс), 7 время паузы/конца, 8 строка из команды (поле 40), 9 (у progress), 10 и 15 константы, 12 = 1.0, 14 диагностика
  (`mark`, `vsid`, `buffering`, `rss_mem`, `rss_lim`, `bitrate`, `conbytes`, `conconlen`, `conpos`, `conretry`, `constate`,
  у ENDED ещё `played_sec`), 17 (у flag).
- **Сверка:** `TestEventsMatchRecordings` строит событие из команды и «входов» (позиция, uuid, vsid, метки времени, diag) и
  сравнивает с настоящим **побайтно: 1432 события из 6 записей, 0 расхождений.** Положительный контроль: сломанное правило
  (поле 18 или константа −14.0) даёт расхождение на всех 1432 событиях. Не синтезируются события вида 5 («diag» без
  состояния): кому они нужны, неизвестно; platformd без них продолжает работать.

**Источник звука Яндекса (`internal/music`)**
- Поток `…/aac192-mp4`: обычный (не фрагментированный) MP4, AAC-LC, 44,1 кГц стерео; `ftyp`, `uuid`, затем `moov` (≈39 КБ)
  с таблицами `stsz/stco/stsc/stts`, потом `mdat`. **Шифрование — AES-128-CTR, нулевой начальный вектор, ключ = поле 1.39 команды
  (hex, 16 байт)**; счётчик = номер 16-байтного блока от начала файла, поэтому читать можно с любого смещения (Range).
- Разбор таблиц на Go даёт длительность (совпала с прогрессом GStreamer, 220288 мс) и перемотку: Range-запрос с байта нужного
  кадра, кадры оборачиваются в ADTS и идут в `maind --gst-launch "fdsrc fd=0 ! aacparse ! avdec_aac ! audioconvert !
  audioresample ! audio/x-raw,rate=48000,channels=2,format=S16LE ! fdsink fd=3 sync=false"`. PCM читается из fd 3
  (stdout занят журналом maind). В GStreamer колонки есть `fdsrc fdsink filesrc filesink decodebin qtdemux aacparse
  avdec_aac mpegaudioparse avdec_mp3 souphttpsrc queue typefind audioconvert audioresample`; нет `audiotestsrc`, `faad`,
  `mpg123audiodec`. Декодер быстрее реального времени ≈18×.
- Зеркала (поле 42) перебираются при ошибке; обрыв чтения кадра повторяется (в живом прогоне один раз сработало: CDN сбросил
  соединение, звук не прервался).
- Вывод: ринг 4 с PCM между декодером и `aplay -c 2` (давление на декодер и скачивание). Пауза обрывает `aplay` (SIGINT),
  источник и буфер остаются как кэш плееров mediad (один плеер на паузе, закрывается через 30 минут или при запуске другого трека).
- **Нормализация громкости:** поле 21 команды (`f1` — истинный пик, дБ; `f2` — громкость трека, LUFS), цель −14. Поправка =
  −14 − f2 (у семи треков из записей от −1,7 до −8,3 дБ), не выше запаса до пика. Формулу mediad в прошивке прочесть
  нельзя, это **догадка по смыслу полей**: без неё музыка играла бы громче штатной на 2–8 дБ. Приглушение на время диалога
  (`DuckGain` = 0,25) и нарастание 150 мс при старте — тоже догадки.

**Замеры (колонка, один трек играет, 10 с)**

| | CPU (доля 1 ядра) | Pss |
|---|---|---|
| штатный mediad | 17,3 % | 21 МБ |
| шим `-music` (omd + декодер + aplay + простаивающий mediad) | 3,1 + 5,8 + 3,6 + 0,7 = 13,2 % | 12,6 + 12,1 + 0,5 + 16,2 = **41 МБ** |

Заранее открытый следующий трек добавляет ещё один декодер (≈12 МБ). Свободной памяти осталось ≈99–108 МБ из 244.
Открытие потока холодным: 0,56 с (HTTPS, moov, запуск декодера, 300 мс звука); от `play` до `PLAYING` без prefetch 0,54 с
против 0,63 с у штатного пути; с prefetch 60 мс против 21 мс (таймеры Go под нагрузкой, вклад не исследован).

**Ошибки, найденные в ходе работы**
- Золотой тест проверял задержку по той же константе, что и код (тавтология): мутация константы его не ловила. Теперь числа в
  тесте взяты из записей, мутация даёт падение.
- Утечка: плеер на паузе оставался в кэше навсегда с живым декодером (≈9–12 МБ на каждую паузу). Теперь один плеер на паузе,
  закрытие при запуске другого трека и через 30 минут.
- Первый `focus` задержал кадр шины на 83 мс: клиент HTTP читал хранилище сертификатов. Теперь `Engine.Warm()` при старте.

**Известные отличия и пробелы**
- **Визуализация музыки пропадает.** С музыкой у штатного пути идёт ≈21 + 45 кадров/с iohub (спектр для дисплея/светодиодов),
  при `-music` ≈1 + 5. Спектр даёт GStreamer-элемент `spectrum` в mediad; нужен свой (БПФ по PCM, 513 полос, 40 мс) и разбор
  формата сообщений iohub. Это следующий шаг; пока `-music` на постоянной основе включать нельзя.
- **Не проверено на слух:** уровень после нормализации, глубина приглушения, нарастание, щелчок при паузе (`aplay` обрывается).
- Естественный конец трека проверен только через перемотку за конец (ENDED с позицией, равной длительности; platformd
  пошёл к следующему); конец по реальному окончанию не ждали.
- Не проверено: перемотка «назад», мультирум и стереопара, Bluetooth-плеер, работа больше нескольких минут, эквалайзер
  (команды `equalizer` идут mediad, нашим звуком не применяются), кнопки на корпусе, возобновление после 30 минут, перезапуск
  platformd с включённым шимом, обрыв сети на середине трека (тогда трек считается законченным).
- `AUDIO_REWIND`: после нашей перемотки platformd не прислал pause+play с новым смещением, как это было у штатного пути;
  звучание продолжилось с нового места, события отражают его.
- Диагностика: `rss_mem` и `bitrate` в событиях — константы, `conbytes/conconlen` настоящие.
- **Громкость колонки.** Master сейчас 27 %: это изменение сделал пользователь, не шим (шим громкость железа не трогает,
  приглушение — программное внутри движка). В ответах на «включи музыку» приходит директива `process_smart_volume_directive`
  (в `quasar.cfg` включён `smart_volume` с порогами по шуму): возможное объяснение прежнего самопроизвольного
  изменения 115→126, но проверено не было.
